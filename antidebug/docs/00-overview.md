## 1. 我们在做什么

给 x64dbg（一个开源调试器）写一个叫 **antidebug** 的插件，用来调试"带反调试保护"
的程序（比如 VMProtect 加壳的程序）。

**反调试**：程序自己检查"我是不是被调试器盯着"，是就拒绝运行。
**反反调试**：我们把这个检查骗过去，让调试可以继续。这就是本插件的全部目的。

插件分三个部分，装在一起用：

| 部分 | 形态 | 干什么 |
|---|---|---|
| 内核驱动 | antidebug.sys | 真正干活：在内核里拦截 10 个跟调试有关的系统调用，把结果改写成"没有调试器" |
| 加载器 | 用户态静态库（链进插件和命令行工具） | 驱动没有签名，不能正常加载；加载器借 Intel 网卡驱动（iqvw64e.sys）的漏洞把它"手动映射"进内核 |
| x64dbg 插件 | antidebug.dp64 / antidebug.dp32 | 你看到的界面：菜单、命令、控制面板对话框 |

另有独立的命令行工具 **antictl.exe**（与插件共用加载器代码），用于不打开 x64dbg
也能加载/停止驱动、做冒烟测试。

## 2. 三份"血统"——代码从哪来

本项目不重复发明轮子，三样核心东西各有一个经过验证的来源，我们做的工作是
**抽象、移植、组合**：

| 来源 | 拿来什么 | 我们改什么 |
|---|---|---|
| `D:\project\vmp\vmp`（约 2500 行驱动） | 10 个系统调用钩子的处理函数（业务逻辑），语义原样保留 | 拆掉 if/else 硬编码派发，改成"技术注册表"；补上按进程过滤和开关；扔掉死代码 |
| `antidebug\InfinityHookPro\`（参考克隆） | hook 引擎：利用 ETW 时钟指针拿到每次系统调用的回调机会，兼容 Win7~Win11 24H2 | 封装成可替换的 `IHookEngine` 接口；修复停止时未完全还原的缺陷；池标签换成自己的 |
| `D:\project\vtdbg`（虚拟化调试器工程） | 驱动加载手法：iqvw64e.sys 字节内嵌 → 注册表 + NtLoadDriver → `\\.\Nal` 拿内核读写能力 → 重定位修导入 → 劫持 NtAddAtom 调用驱动入口 → "启动邮箱"轮询确认 | 把原语来源封装成可替换的 `IPrimitiveProvider` 接口；入口协议换成我们的 |

另有 `antidebug\TitanHide\`（参考克隆）：插件 SDK（pluginsdk 头文件和 .lib）从这里复制，
插件骨架（pluginit/菜单/命令/事件回调）以它为参考。

## 3. 一句话原理

Windows 程序调用系统服务时要经过内核的一张函数表（SSDT）。直接改这张表会触发
内核的自我保护（PatchGuard，触发即蓝屏），所以我们不走这条路：利用系统自带的
事件记录机制（ETW，Event Tracing for Windows）里的一个"取时钟"函数指针——
每次系统调用发生时它都会被调用——在那一瞬间查看调用栈，找到"这次系统调用
即将跳去哪个内核函数"，把目标临时换成我们的处理函数；处理函数调回原函数后，
把结果改写成"未被调试"的样子再返回。这个手法叫 InfinityHook。

## 4. 目标用户和使用方式

- 使用者：逆向分析人员、安全研究人员（用自己的机器、调试自己有权分析的程序）。
- 典型流程：管理员权限装好驱动 → x64dbg 打开目标程序 → 插件自动（或手动）把
  被调试进程加入"隐藏名单" → 目标程序的反调试检查全部落空。
- 所有"技术"（11 项，见 docs/03）可以单独开关；隐藏名单按进程 PID 管理，最多 8 个。

## 5. 不做什么（边界）

1. 不做用户态的反反调试（不注入 DLL 进目标进程、不改目标进程的 PEB）——
   用户态方案对 VMProtect 这类强保护无效，这正是要写内核驱动的原因。
2. 不做时间类反调试的对抗（rdtsc / GetTickCount 检测）——vmp 参考工程没做，
   引擎手法（改时钟来源）反而可能影响计时，docs/06 有说明。
3. 不做驱动签名——走手动映射路线，代价见 docs/06（需要关闭系统的一些防护）。
4. 不支持 32 位 Windows——引擎和映射手法都只在 x64 内核上成立。
5. CE（Cheat Engine）的 dbk64.sys 驱动只做文档化备选，不实现（docs/09）。
